# 대용량 DB와 외부 백업 복구 검증

실제 장비, 운영 DB, USB/NAS/클라우드에 접속하지 않고 합성 데이터와 격리된 경로로 검증합니다.
원본 저장소는 읽기 전용이며 모든 변경은 `auto_network`의 별도 PR에서 검증합니다.

## 재현된 문제와 수정

| 문제 | 영향과 수정 |
|---|---|
| 최신 uptime 조회가 모든 과거 행에서 상관 부질의를 반복 | 응답 없는 장비의 NULL 이력이 길면 점검 시작이 지연됨. 유효 uptime 부분 인덱스와 장비별 최신 회차 탐색으로 변경. 최신 NULL을 건너뛰는 기존 의미와 장비 세대 정보를 보존 |
| VRRP 시간 정렬·중복 확인·미확인 개수 조회가 전체 이력을 처리 | 화면 조회/점검 저장 지연. 시간 표현식·장비/본문·미확인 부분 인덱스 추가. 동일 로그 중복 처리와 ack·NULL 정렬 의미 보존 |
| 짧은 추이 조회가 장비의 전체 이력을 탐색 | 회차 시간 인덱스로 요청 범위를 먼저 선택. 응답 순서는 기존 회차 ID 순서 유지 |
| 만료 회차마다 Python에서 삭제 SQL 3개 실행 | 오래된 ID 목록을 메모리에 만들고 수많은 SQL을 실행. 하나의 트랜잭션에서 집합 삭제, 과거 미확인 VRRP와 시간 불명 기록 보존 |
| 백업 복사·무결성 검증 동안 앱의 DB/설정 잠금을 계속 보유 | 상태 화면·저장·종료 요청이 전체 백업을 기다림. 별도 읽기 전용 SQLite 연결로 온라인 백업하고 설정 잠금은 요청 승인 시에만 사용 |
| 외부 복사본의 구조 검사는 성공해도 내용 변경을 검출하지 못함 | `.ncbak` 한 파일에 고정 DB 항목과 SHA-256·크기 manifest 포함. 스트리밍으로 CRC·digest·스키마 확인 후 새 파일로만 복원 |
| 파일 확정이 hardlink 한 방식에만 의존 | 명확한 미지원 오류일 때 Windows/macOS native exclusive rename으로 대체. 경쟁자가 먼저 만든 대상은 보존. 안전한 방식이 없으면 실패 |

## 조회 성능 비교

macOS Python 3.12.14 / SQLite 3.53.1, 같은 합성 스키마와 데이터에서 비교했습니다.
이 수치는 해당 호스트의 측정값이며 다른 하드웨어의 응답 시간을 보장하지 않습니다.
작은 프로파일은 1,000회 × 100대, 큰 프로파일은 10,000회 × 100대입니다.
VRRP·이벤트는 각 100,000행이며 각 장비 회차에 압축 원본 1개를 저장했습니다.

| 항목 | 수정 전 | 수정 후 |
|---|---:|---:|
| 10만 장비 결과의 최신 uptime | 0.694초 | 0.00239초 |
| 100만 장비 결과의 최신 uptime | 10초 제한 초과 | 0.0216초 |
| VRRP 최근 300건 (큰 프로파일) | 0.0489초 | 0.000441초 |
| 큰 프로파일의 DB 크기 | 385.4MB | 418.3MB |
| 큰 프로파일의 만료 이력 정리 | 0.844초 / SQL 15,002개 | 1.267초 / SQL 7개 |

인덱스는 조회를 개선하지만 저장 공간과 삭제 비용을 늘립니다. 보관 정리의 약 50% 시간 증가를 성능 개선으로
표현하지 않습니다. 인덱스 최초 추가는 큰 프로파일에서 약 0.432초였습니다. 완료된 전후 조회는 결과 SHA-256이
일치했고, 수정 전 시간 초과한 최신 uptime은 독립적인 fixture 기준으로 장비별 마지막 유효 회차를 확인했습니다.
회귀 테스트는 짧은 시간 제한 대신 SQLite VM 실행량·결과 의미·보관 후 잔여 데이터·rollback을 검사합니다.

## 1GiB 종단 검증 프로파일

```sh
python tests/db_scale_check.py --runs 10000 --devices 100 --raw-bytes 1536 --min-db-bytes 1073741824 --output db_scale_check.json
```

사용 중인 SQLite 페이지 크기와 실제 파일 크기가 모두 1GiB 이상인지 확인합니다. 빈 파일 확장이나 freelist로
크기만 부풀리지 않으며, 압축 전 원본 길이와 평균 압축 크기, 각 테이블 행 수를 기록합니다.
메모리 사용을 제한한 batch 생성, 조회·원자 저장·온라인 백업·패키지 내보내기·격리 경로 전송·복원·보관 정리를
측정합니다. 복구 시 원본 작업 경로를 사용할 수 없게 하고, 전체 논리 데이터 digest와 원본 출력·보고서 문맥 등을
대조합니다. stdout 로그와 JSON에는 Python/SQLite/OS, 실제 저널 모드, 단계별 시간·파일 크기·메모리 관측을 남깁니다.

최종 코드의 macOS 실행은 통과했습니다. 실제 파일·사용 페이지는 **1,959,682,048 bytes (1.825GiB)**,
장비 결과·압축 원본은 각각 1,000,000행, 이벤트·VRRP는 각각 100,000행이었습니다.
전체 50.20초, 프로세스 최대 RSS 176,062,464 bytes (167.9MiB)를 관측했습니다.
온라인 백업과 외부 패키지 복원 후 모든 테이블·스키마 digest가 일치했고 원본 파일 SHA-256도 유지됐습니다.
만료 1,360회차를 정리한 뒤 미확인 VRRP 50,001행의 전체 digest를 확인했습니다.
이 결과는 동일 호스트의 격리 경로 실험이며 실제 외부 장치 성능은 포함하지 않습니다.

기존 GitHub Actions `windows-latest` / Python 3.12 작업에 같은 프로파일을 포함합니다.
Windows의 최종 판정은 해당 PR 및 병합 커밋의 성공 로그이며 macOS 결과로 대체하지 않습니다.
시간 기준은 느린 CI를 허용하는 상한이며 응답 시간 SLA를 뜻하지 않습니다.

## 장애·복구 판정

- 백업 중 검증과 복사 단계를 각각 멈춘 상태에서도 조회·원자 저장·상태/종료 요청이 진행되는지 Event 순서로 검사합니다.
- 전송 후 SHA-256을 확인하고 원본 폴더가 없는 상태에서 새 DB로 복원합니다. 회차·원본·기준값·이벤트·VRRP·보고서 문맥을 보존합니다.
- 잘림·bit flip·CRC 오류·유효 SQLite 내부 값 변경·잘못된 manifest·중복/경로/암호화 항목을 거부합니다.
- 공간 부족·권한 오류·중간 복사 실패·시간 초과·동일 대상 경쟁에서 기존 파일을 보존하고 미완성 결과를 발행하지 않습니다.
- 빌드된 Windows EXE로도 내보내기·전송·원본 없이 검증/복원·덮어쓰기/손상 거부를 실행합니다.

패키지는 DB만 포함합니다. 설정과 OS 저장 계정은 별도이며 실제 운영 DB 교체를 자동으로 수행하지 않습니다.
실제 외부 장치의 장애·전원 차단·장기 성능, 네트워크 파일시스템의 의미, 발행자 인증 및 실제 운영 복구는 미검증입니다.
OS 파일 I/O 자체가 멈춘 경우 소프트웨어 제한 시간은 해당 호출이 반환되어야 확인할 수 있습니다.

설계 근거: [SQLite online backup](https://www.sqlite.org/backup.html),
[SQLite query plan](https://www.sqlite.org/eqp.html), [Python sqlite3](https://docs.python.org/3.12/library/sqlite3.html).
